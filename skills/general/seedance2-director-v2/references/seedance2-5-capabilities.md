## The four things that actually change how you write

### 1. Timestamps now work
2.0 ignores clock times and only honours shot numbers. 2.5 responds to
integer-second timestamps, so a timeline is a real control surface.

Three ways to place events, all valid:

| Form | Example |
|---|---|
| Intervals | `0-3s ... 3-7s ... 7-15s` or `[1s-4s] ... [4s-8s]` |
| Single points | `At the 5-second mark, a quick left wipe.` |
| Relative | `After 3 seconds, everyone around him shakes their head.` |

Rules that keep it from degrading:
- **No gaps.** `0-3s ... 5-6s` leaves the model to improvise the hole.
- **Balance the load.** Too little content in a window invites improvisation;
  too much causes extra cuts or dropped beats.
- **Don't timestamp high-frequency motion.** "Shake your head three times per
  second" is not a timing instruction the model can honour.

### 2. Length and reference budget go up hard
- Up to **30 seconds** in a single generation (2.0 tops out around 15s).
- Up to **50 reference assets** in one request:
  - ≤ 30 images, up to 4K
  - ≤ 10 videos, ≤ 30s combined
  - ≤ 10 audio clips, ≤ 30s combined

Practical sweet spots the docs call out — exceed these and you trade stability
for ambition:

| Reference type | Comfortable | Stretch (expect retries) |
|---|---|---|
| Subject image refs | 1–8 subjects | 9–12 |
| Subject audio/video refs | 1–5 subjects | 6–10 |
| Subject ref clip length | 5–10s | longer |
| Storyboard panels | ≤ 15 | more |
| Video to edit | ≤ 20s | longer |
| Ref images for a video edit | 1–5 | 6–8 |

Multi-view subject images are now supported (2.0 discouraged them). Past five
subjects, prefer single-view images, and split views into separate images
rather than tiling several viewpoints into one.

### 3. Aspect ratio is no longer six fixed buckets
2.5 will produce any ratio in **[0.4, 2.5]**, driven by the input assets. Which
brings us to the one thing that trips up integrations:

### 4. Locked vs unlocked tasks
Some task types pin output parameters to the input asset. Send the wrong
parameter and the request is rejected, not silently coerced.

| Task | What locks | What you must send |
|---|---|---|
| **Editing** | ratio *and* duration | `ratio=adaptive`, `duration=-1`, prefer `output_format=mov` |
| **First / first+last frame** | ratio only | `ratio=adaptive`; duration is yours |
| **Extension** | ratio only | `ratio=adaptive`; duration is yours; prefer `output_format=mov` |
| Reference, storyboard, keyframe | nothing | ratio and duration are yours |

Editing output can drift from the source by up to ~0.3s (transition frames get
compressed) — unless the source was itself generated by 2.5, in which case
durations match exactly.

Locked tasks are triggered by a combination of asset roles *and* prompt wording:

- **Editing** — roles `reference_image` / `reference_video` / `reference_audio`
  plus an edit verb in the prompt: *edit video, add, insert, remove, delete,
  modify, replace, change to*.
- **Extension** — same roles plus: *extend forward, extend backward, continue,
  continue from, extend the story*.
- **First/last frame** — set `role` to `first_frame` / `last_frame` directly.

If several videos are attached, the model reads the prompt to decide which one
it is editing or extending. Name it explicitly.

## Prompt shape

Same visual-storytelling posture as 2.0, four parts:

1. **Asset bindings** — every image/video/audio named by upload order and role.
2. **One-sentence summary** — subject + location + event + genre/style + camera.
3. **Detailed plot** — timeline or shot list; per segment give visuals, camera,
   action, dialogue, sound.
4. **Consistency notes** — what holds across the whole piece: camera character,
   environment, palette, atmosphere, audio bed.

Positive phrasing throughout. Negative control is only reliable for subtitles
and audio: `No subtitles.` · `No BGM; environmental and action sounds only.` ·
`No audio.`

### Binding references (the highest-leverage rule)
Numbering follows upload order — `Image 1`, `Video 1`, `Audio 1`. Bind every
asset in the *text*, not by writing a name onto the image.

```
Images 1-2 are Character 1 and correspond to Audio 1;
Images 3-4 are Character 2 and correspond to Audio 2.
Refer to the spell-casting action in Video 1 and the wrap-around camera move in Video 2.
Refer to Image 1 for lighting and filters only.
```

State what each asset is *for*. If only part of an asset applies, say which
part. And when a reference is already accurate, say "strictly refer to it" and
stop describing it — re-describing what the asset already shows fights it.

### Camera language
Write shot size, movement, and angle plainly — extreme wide / wide / medium /
medium close-up / close-up; push in, pull out, pan, track, follow, orbit, dive,
tilt up, handheld shake; low angle, overhead, first-person. Named techniques
work directly too: one-shot / long take, dolly zoom, FPV, bullet time, speed
ramp, aerial.

For anything niche, write `[term] + [what it looks like]`:
> Rack focus: the focus shifts smoothly; the foreground trees go soft while the
> character behind them resolves.

For transitions, always give **both** the trigger point and the method:
> At the 5-second mark, the camera wipes left into a natural dissolve.

### Action and expression
Describe actions generally ("a few sets of high-knee raises and a somersault",
"both sides trading close-quarters strikes"); reserve specific choreography for
the one or two moments that must land. Write expressions as descriptions, not
idioms.

## Capabilities 2.0 doesn't have

**3D clay-model reference (previz rendering).** Feed a grey-box animatic and
have 2.5 render it into a finished style. Say explicitly which channels to take
from the clay video — camera movement and motion only, or lighting changes too.
Coarse, simple geometry works better than detailed models; strip trajectory
lines, camera cones and coordinate grids out of the render. Map each grey proxy
to a reference image by name: *"map the man in grey from Image 1 to the red
model in Video 1."* Then still describe the intended output fully — the clay
video controls motion, not appearance.

**Multi-panel storyboards.** One image containing several panels gives a
high-level plot reference, not a frame-accurate one. Keep it to ≤ 15 panels,
use line art or stick figures, keep text off the image, and use the prompt to
fill in everything the panels don't show (style, camera, timing).

**Keyframe reference.** When the video *must* follow the boards, upload each
panel as its own image and open the prompt with
`Use Images 1 to N in order as keyframes.` This aligns far more strictly than a
multi-panel storyboard.

**Video editing.** Add / modify / remove visual or audio elements in an existing
video, optionally scoped by timestamp, optionally guided by reference images.
Phrase edits as A → B: *"from 4-6s change his action from drinking coffee to
mopping the floor; leave everything else unchanged."*

**Video extension.** Continue a clip forward or backward, with optional subject
references. Use `mov` in and out for clean audio-visual continuity.

**Seamless transition.** Give two clips and have 2.5 generate the missing
in-between so they join without a visible seam.

**One-click video creation.** Assemble a set of images and/or clips into a short
with optional text, stickers and transitions.

## Choosing 2.0 vs 2.5

Reach for **2.5** when the shot needs: length over 15s, timestamped beats,
more than a handful of references, a non-standard aspect ratio, editing or
extending existing footage, clay-model previz, or strict keyframe adherence.

Stay on **2.0** when it's a single self-contained shot under 15s with one or two
references — it is the cheaper, more proven path and the prompt grammar is
simpler. The 2.5 release is an incremental production-workflow upgrade over
2.0, not the generational jump that 2.0 was over 1.5.

## API notes (for the backend adapter)

Endpoint: `POST {ARK_BASE_URL}/contents/generations/tasks`
Poll: `GET {ARK_BASE_URL}/contents/generations/tasks/{task_id}` →
`pending | running | succeeded | failed`

The request carries a `content` array rather than flat fields — text item plus
one entry per asset, each tagged with a `role`
(`first_frame`, `last_frame`, `reference_image`, `reference_video`).
Parameters observed on the tutorial page: `resolution` (480p/720p/1080p),
`ratio`, `duration` (4–30, or `-1` for editing), `output_format` (mp4/mov),
`generate_audio`, `watermark`, `seed`, `callback_url`.

Treat the parameter list as indicative and verify against the live tutorial page
before relying on any single field — it was read from rendered documentation,
not from an API schema.

Implemented in `backend/app/services/media_gen_service.py`
(`animate_image_seedance25`) and registered in
`backend/app/services/video_models.py`.

## Field notes — realism, from practitioners

The rules above come from BytePlus. These come from creators shipping 2.5 work,
captured in the Content Intelligence ingest of 2026-08-19
(`reference_documents/content_intelligence_staging/`). Treat them as
well-attested heuristics, not vendor guarantees.

### Scene plate before anything else
Generate the **empty environment** as a still before characters, then inherit
its lighting and palette into every shot. Specify camera angle, time of day,
practical light sources, prop states, and which way signage faces relative to
camera.

Counter-intuitively, don't sanitise it: an overexposed plate with halation
around hot light sources carries a photographed quality into the video. A clean,
evenly-lit plate reads as CG.

Split image models by job — one for environments, one for faces and wardrobe.

### Lock the space, not the first frame
Characters teleporting between generations (different washing machine, different
corner of the room) is a *spatial description* failure. The instinctive fix —
pinning a literal first frame to every shot — trades it for a worse artefact:
motion that reads as an image being animated rather than a scene being filmed.

Instead, carry the same spatial anchors through every prompt in a sequence:
which wall, what's camera-left, what's through the window, where the practicals
are, which way the subject faces.

### The anti-plastic vocabulary
Causes of the plastic look: pinned first frames, sanitised plates, shots that
open on a held pose, and absent texture instructions.

Counters, all of which belong near the **top** of the prompt:
- Optical imperfection — organic film grain, halation, high dynamic range,
  large-format film.
- Material honesty — matte non-reflective surfaces, lived-in worn materials.
- Explicit negation of the wrong register — *not* a 3D render, *not* a game
  engine, *not* a game-cutscene aesthetic. Describing the right look is not
  enough; name the wrong one.
- Never open or close on stasis. Start the character already mid-action.
- Name costumes as costumes. "A human wearing a gorilla costume" and "a gorilla"
  produce different physics and different skin response.

### Top-load the prompt
What sits at the head of the prompt is what the model holds to. Put shot count,
total runtime, per-shot beats, style and texture there — then the scene body.

Applies to negative control too: if background music is bleeding into
generations, move `NO MUSIC WHATSOEVER` / `NO BGM` to the first line rather than
rewording it at the end. This lines up with BytePlus's own note that negative
control is reliable specifically for subtitles and audio.

### Extension is a continuity tool
Before writing an extension prompt, feed the source clip to an LLM and ask it to
analyse each frame — what's happening, where everything sits. Then write the
continuation from that reading, naming what must **not** change as well as the
new action ("his hand stays where it is on the side of the machine"). Joins are
reported as seamless when done this way.

### Gate on a storyboard still
Render one image from the finished video prompt before spending video credits.
It won't predict the final frame — different model — but it catches wrong
composition, wrong environment, or a character in the wrong place for a fraction
of the cost.

### Reference-image moderation
2.5 applies strict copyright moderation to reference *images*, and will reject
original designs that merely resemble a known character. Where the design is
genuinely yours, move it from the image channel to the text channel: describe
the wardrobe in the prompt and supply a body reference in plain clothing, so the
model layers the described outfit on. This routes around an over-eager
similarity filter; it does not make someone else's design usable.

### Failed generations are takes
Budget for them. Pull the good two or three seconds out of each near-miss and
cut them together, the way coverage works on a set. A quoted real figure: a
one-minute finished piece at roughly 800 credits (~$32) including throwaways.
